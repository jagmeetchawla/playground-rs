# Rustic Playground — Onboarding Guide

> For a new developer or PM joining the project. Everything you need to understand what this is, where it came from, how it's built, and where it's going.

---

## 1. What Is This?

**Rustic Playground** is a macOS desktop app for running Rust experiments — inspired by Swift Playgrounds.

You write a `.rs` file, hit **Run** (`⌘R`), and see live compiler output and program output stream into the console panel below the editor. No terminal, no project setup, no context switching.

Each experiment is called a **playground** — a standalone Rust `fn main()` binary target. Related playgrounds are grouped into a **project** — its own Cargo workspace with its own `Cargo.toml` and dependency set. You can have multiple projects (e.g. one for algorithms, one for async experiments) and switch between them instantly.

**Target user:** A developer learning Rust, prototyping ideas, or working through a book/course — someone who wants the speed and convenience of a REPL-like environment without leaving a GUI.

---

## 2. Product Evolution

The product started as a CLI runner and has been iteratively turned into a full GUI desktop app. There have been three distinct eras:

### Era 0 — build.rs macro approach (`playground-rs-alt/` (deleted))
The original proof-of-concept used `build.rs` to scan source files and generate a dispatcher macro. Clever but fragile. Replaced because Cargo's native `src/bin/` auto-discovery does the same thing with zero code.

### Era 1 — CLI runner (`src/main.rs`) — tagged `v0`, `v0.1`
A simple `clap` CLI: `cargo run list`, `cargo run hello`, `cargo run` (interactive picker). This still works today and is preserved in the codebase. It shares the same `src/bin/*.rs` playground model that the GUI app uses underneath. See [`specs/archive/specs-v1-cli.md`](specs/archive/specs-v1-cli.md).

### Era 2 — Tauri desktop app — `v1.0` through `v0.1.6.1` (current)
The CLI runner was wrapped in a [Tauri 2](https://tauri.app) + [Svelte 5](https://svelte.dev) GUI with a Monaco editor. The playground model stayed unchanged — only the interface changed. The versioning reset from `v1.x` to `v0.1.x` when the project was restructured to reflect that it's still pre-1.0 quality. See [`specs/architecture.md`](specs/architecture.md).

## 3. Tech Stack

| Layer | Technology | Role |
|-------|-----------|------|
| App shell | [Tauri 2](https://tauri.app) | macOS window, native menus, IPC bridge, WKWebView host |
| Backend | Rust (`src-tauri/src/lib.rs`) | File I/O, process management, Cargo invocation, menu building |
| Frontend | [Svelte 5](https://svelte.dev) + Vite | UI components, reactive state (runes: `$state`, `$derived`, `$effect`) |
| Editor | [Monaco Editor](https://microsoft.github.io/monaco-editor/) | VS Code's editor engine, syntax highlighting, tab management |
| Styling | CSS custom properties | Dark theme, consistent design tokens in `App.svelte` |

The frontend runs in macOS's WKWebView (Tauri's rendering layer) and communicates with the Rust backend through Tauri's IPC bridge (`invoke()` calls for commands, `listen()` + `Channel` for streaming).

**Key constraint:** The app is intentionally **not sandboxed**. Like Xcode and Terminal, it must compile and execute arbitrary Rust code using the user's local toolchain. Any playground runs with full system access.

## 5. How the Core Loop Works

```
User edits code in Monaco
    ↓
⌘S  →  invoke('save_playground', { name, content })
    ↓  writes to ~/Library/Application Support/com.rustic-playground.app/
    ↓             projects/<project>/src/bin/<name>.rs
    ↓
⌘R  →  invoke('run_playground', { name, channel })
    ↓  backend spawns: cargo run --bin <name> --target-dir playground-runs/
    ↓  process group set (process_group(0)) so Stop can kill cargo + binary together
    ↓  streams stdout/stderr line-by-line through Tauri Channel
    ↓  frontend appends lines to the active RunBlock in Output.svelte
    ↓  on exit: RunBlock status → 'success' or 'error'
```

Each run appears as a collapsible block in the output panel. The block separates **Compiler** output (rustc warnings/errors, in a distinct dark code box) from **Program** output (your program's stdout/stderr).

### Process kill
`cargo run` spawns in its own process group (`.process_group(0)`). When Stop is pressed, `kill_playground` sends `SIGTERM` to the entire process group (`kill -TERM -<pgid>`), waits 300ms, then `SIGKILL`. This ensures both `cargo` and the compiled binary die.

### Content files
Each playground has a **content folder** at `projects/<project>/content/`. The app injects `PLAYGROUND_CONTENT=<path>` as an environment variable so playground code can read files at runtime — same concept as Swift Playgrounds' assets bundle.

## 6. Data Storage

All user data lives at:
```
~/Library/Application Support/com.rustic-playground.app/
├── config.json                  ← active project name
└── projects/
    └── <project-name>/
        ├── Cargo.toml           ← shared deps for all playgrounds in this project
        ├── src/bin/
        │   ├── hello.rs         ← seeded on first launch
        │   └── <name>.rs
        └── content/
            └── <name>/          ← content files for each playground
```

On first launch the `default` project is created with a seeded `hello.rs`. You can delete this entire folder to reset to a clean state during development.

## 9. Methodology — How We Work

### Specifications
Every version has a written spec before implementation begins. The spec lives in [`specs/specifications.md`](specs/specifications.md) while active, then is archived to `specs/archive/specs-v<N>.md` when the version ships. A spec includes: problem statement, goal, backend design (structs, commands, data flow), frontend design (components, state), and acceptance criteria. See [`specs/workflow.md`](specs/workflow.md).

### Development workflow
1. Read [`AGENTS.md`](AGENTS.md) and [`specs/workflow.md`](specs/workflow.md) first
2. Read the active spec before any feature work
3. Read [`specs/architecture.md`](specs/architecture.md) when making structural decisions
4. Implement in small focused diffs — commit each logical change separately
5. Archive the spec and create a GitHub Release when the version ships
6. Write the next spec before starting the next version

### Releases
- Versions tagged in git (`v0.1.5`, `v0.1.6`, etc.)
- Patch fixes get a `.1` suffix (`v0.1.6.1`) and are described as bug-fix-only on top of the parent
- GitHub Releases created for each tag with a human-written changelog

### Known Tauri/WKWebView gotchas
These have burned us more than once:

| Gotcha | Symptom | Fix |
|--------|---------|-----|
| `window.confirm()` / `window.alert()` | Silently return `false` — action appears to do nothing | Replace with in-app modal (use `$state` + conditional render) |
| Monaco swallowing keyboard events | `⌘S`, `⌘R` etc. don't fire when editor is focused | Route through native menu accelerators (Tauri `on_menu_event`), not DOM listeners |
| Menu item enabled state | `menu.get(id).set_enabled()` is unreliable after menu rebuilds | Rebuild the entire menu with correct `.enabled()` baked in at construction time |
| Process kill hitting only cargo | Compiled binary keeps running after Stop | Spawn with `.process_group(0)`, kill by `-pgid` |
| Sidebar content not resizing | Inner component ignores parent resize | Use `width: 100%` inside components, not hardcoded CSS variables |

### Svelte 4 vs Svelte 5 migration note
The codebase is mid-migration. Newer components use Svelte 5 runes (`$props()`, `$state()`, `$derived()`, `$effect()`). Older components (`Sidebar.svelte`) still use Svelte 4's `createEventDispatcher`. Both work, but don't mix patterns within a single component. New code should use the Svelte 5 callback-props pattern.

### Native menu management
The full menu bar is built by `build_menu()` in `lib.rs` on every state change that affects menu content. The frontend calls `invoke('rebuild_menu', { projects, active, playgroundCount })` reactively via `$effect` whenever the projects or playgrounds list changes. Enabled/disabled states are baked in at construction time — do not try to toggle them post-hoc via `set_enabled()`.

## 10. Getting Started (Developer Setup)

**Requirements:** macOS 11+, Rust + Cargo, Node.js 18+, Tauri CLI 2.x

```sh
git clone https://github.com/jagmeetchawla/rustic-playground
cd rustic-playground

# Install Tauri CLI if needed
cargo install tauri-cli --version "^2.0"

# Development — hot reload (Vite + Tauri)
cargo tauri dev

# Production build (.app + .dmg)
cargo tauri build
```

App data is stored at `~/Library/Application Support/com.rustic-playground.app/`. Delete this folder to start fresh.

**Regenerate app icon:**
```sh
pip3 install Pillow
python3 gen_icon.py                                          # produces src-tauri/icons/app-icon-source.png
cargo tauri icon src-tauri/icons/app-icon-source.png         # generates all sizes
```
